How skima works

skima is a small command-line tool that tells you which of your agent skills you actually use, and keeps every agent pointed at the same set of skills.

Written from ~/projects/skima/SPEC.md, 2026-10-12. Every number below was measured on this machine.

What it is

You have 29 skills in ~/dotfiles/skills/. Four agent homes use them: Claude Code (~/.claude), your work Claude profile (~/.claude-work), Codex (~/.codex) and Pi (~/.pi/agent). skima answers three questions about them:

  1. Which skills actually get loaded, on which agent, how, and when?
  2. Which skills are dead weight?
  3. Does every agent home see exactly the right skills, with the right settings?

The idea comes from MoltenBase, which does usage tracking and syncing for teams. skima is the one-person version. It drops accounts, cloud sync and the web dashboard. It adds three things a single person with a git repo of skills needs: a usage history that never expires, a source line for every number, and a link to your existing grade and retro results.

It's a single Rust binary that runs in the terminal, and its output is plain text. Add --json when an agent needs to read it.

Why build it

Three problems exist on this machine today.

A skill is silently missing from one home

The current installer, skills/install.sh, has a hard-coded list of places to link skills into. Your work profile isn't on it. The result:

$ diff <(ls ~/.claude/skills) <(ls ~/.claude-work/skills)
3d2
< break-invariants

So when you work under the cw alias, break-invariants doesn't exist. Nothing told you.

Claude Code is deleting your history

Claude Code deletes session files older than 30 days unless cleanupPeriodDays says otherwise, and it isn't set here. During the planning session itself, the oldest session on disk moved from 2026-09-06 to 2026-09-10. Every day before skima's first scan, another day of usage evidence disappears. After that first scan the deletion stops mattering, because skima has already copied each load into its own file. The logs only need to last until the next scan.

A text search can't tell which skills are used

A plain text search for a skill name is wrong most of the time. For example, searching Claude's logs for <command-name>/validate-findings-backlog matched 73 lines on 2026-10-12, but only 3 were real uses. The other 70 are the name quoted inside tool output or prompts. You need a tool that knows what a real load looks like.

Where the numbers come from

Every agent already writes a log of each session to disk. When a skill loads, that log gets a specific, structured line. skima reads those logs. It installs no hooks and changes nothing in the agents.

A hook would only see loads from the day it was installed. Reading the logs gives months of history on the first run. Codex logs go back to 2026-03-29. Claude's typed commands go back to 2026-02-24.

The rule for every agent is the same. Count only the line the agent itself writes when it loads a skill, never a mention of the skill in text. Here is what that line looks like on each agent:

AgentYou do thisThe log records
Claude CodeType /unslopA hidden user message starting Base directory for this skill: …/unslop
Claude CodeThe model decides to call the Skill toolThe same hidden message, plus a link to the tool call, plus success: true
CodexType $gradeA user message starting <skill><name>grade</name><path>…
PiType /skill:goal-smartA user message starting <skill name="goal-smart" location="/…/SKILL.md">
AnyThe model runs cat …/grade/SKILL.mdA shell or file-read tool call on that path

Built-in commands like /clear also show up in Claude's log, but they never get the "Base directory" line, so skima ignores them.

Strong and weak loads

skima records how each skill got into the model's context. It calls this the channel.

ChannelKindExample
slashstrongYou typed /unslop, $unslop or /skill:unslop.
toolstrongClaude called its Skill tool for unslop and the call succeeded.
typedstrongAn old /unslop line in ~/.claude/history.jsonl whose session file is already deleted. Recovered once, on the first scan. Plugin commands such as /argus:triage don't count.
readweakThe model ran sed -n '1,200p' unslop/SKILL.md.
refweakThe model read unslop/references/prose-tells.md. Reading a skill's scripts or tests doesn't count: those aren't instructions.

Reads are weak because a read can mean two things. The model may be reading grade/SKILL.md to follow it, or because you asked it to edit or grade that skill. skima can't always tell which.

Reads still matter a lot. Codex and Pi hide skills from the model, so your AGENTS.md rule makes the model read SKILL.md by path instead. One planner counted 1,472 Codex reads against 167 $name loads. Ignoring reads would undercount Codex about tenfold. Adding them to the headline would count your skill editing as skill use. So reads get their own columns and are never added to the headline number.

To reduce the editing noise, skima marks a read as "authoring" when the session runs inside your dotfiles repo or an agent's skills folder, or when the same session also loaded grade, retro, writing-for-agents or skill-creator. Authoring reads are hidden unless you pass --authoring.

Who loaded it

Each event also records who was at the keyboard, called the actor:

  • main: you, in a normal session.
  • subagent: a helper agent that a main session started.
  • headless: a scripted run such as claude -p or codex exec.
  • probe: your benchmark and policy-test harnesses. They are hidden by default so they don't inflate the counts.

Counting each load once

The same load often appears in more than one file. skima handles three cases.

Subagents count toward their parent session

If you load blast-radius in a session and three subagents in that session load it too, that is still one session that used blast-radius. skima follows each session back to the one that started it, called the root session, and the headline number counts distinct root sessions.

Forked sessions don't double count

When Codex forks a session or starts a subagent, the new log file starts with a copy of the parent's history. A $grade in the parent therefore appears in both files.

This is the bug the last validation round caught. The spec first assumed the copy keeps the original timestamp. It doesn't. A script over every forked Codex session found that all 186 copied tool calls and all 14 copied $name blocks got a new timestamp but kept the rest of the record byte for byte. So skima builds each Codex event's ID from the record's content and leaves the timestamp out. Both copies produce the same ID and are stored once.

Which copy gets stored? skima reads log files in order of their file name, and Codex and Pi file names start with the session's start time. A parent always starts before its forks, so the parent's copy is stored, with the parent as its actor and source line. A scan from scratch and a day-by-day scan therefore end up with the same ledger.

# parent rollout, 18:31:33.963
{"timestamp":"…33.963Z","payload":{"type":"function_call","call_id":"call_9x…","arguments":"{\"cmd\":\"cat …/grade/SKILL.md\"}"}}
# child rollout, 18:31:37.147: new timestamp, identical payload
{"timestamp":"…37.147Z","payload":{"type":"function_call","call_id":"call_9x…","arguments":"{\"cmd\":\"cat …/grade/SKILL.md\"}"}}
# skima's ID for both: cx:<root session>:sha1(payload):0

Illustrative records. The real ones carry more fields.

Pi copies keep the original entry ID and timestamp, so skima uses those for Pi directly. One Pi entry turned up in 6 different files and is counted once.

Chunked reads count once

Codex reads long files in pieces: sed -n '1,220p', then sed -n '220,440p'. Reports count at most one load per agent, root session, skill and channel. The ledger keeps every raw event, so skima show can still list each piece.

The ledger

skima copies every event it finds into its own file, ~/.local/share/skima/events.jsonl. Once Claude deletes an old session file, this ledger is the only record that the load happened, so skima never deletes from it.

Each line is one event. It stores the skill name, agent, channel, actor, time, working directory and the exact file and line it came from. It never stores your prompts or the skill text.

{"v":1,"id":"cc:toolu_01EKQ5…","ts":"2026-09-15T06:15:31.455Z",
 "agent":"claude","home":"claude","session":"2e112b1e-…","actor":"main",
 "skill":"unslop","origin":"canonical","channel":"tool",
 "cwd":"/home/nicolas/projects/argus","authoring":false,
 "src":"…/-home-nicolas-projects-argus/2e112b1e-….jsonl:412"}

The src field is the point. Any number in a report can be traced to the log line that produced it, and you can open that line yourself.

How it stays correct

  • Each event has a unique ID taken from the agent's own record, such as Claude's tool-call ID. skima appends an event only if its ID is new. Scanning the same file twice adds nothing.
  • A bookmark per file remembers how far skima has read, so later scans only read new lines. The bookmark only saves time. If you delete it, the ID check still prevents duplicates.
  • A lock makes two scans running at the same time take turns.
  • Half-written lines are skipped until the agent finishes writing them, so a live session is never read halfway.

The first scan reads about 1.0 GB of Claude logs, 5.2 GB of Codex logs and 585 MB of Pi logs, and must finish in under 90 seconds. A prototype read 7.27 GB in 58 seconds. After that, each scan reads only what's new and must finish in under 2 seconds.

The ledger is the one file that can't be rebuilt, so it stays out of git (the dotfiles repo goes to GitHub, and the logs contain client paths under NDA) and belongs in your home backup.

The commands

Six commands make the first version. The usage commands scan for new events before printing, so their output is always current. There is no background daemon or timer.

CommandWhat it does
skima scanReads new log lines and adds events to the ledger.
skima usageOne row per skill: sessions, counts per channel, agents, last use, a 30-day sparkline, latest grade.
skima unusedSkills with no strong load in the last 60 days, minus the ones other live skills depend on.
skima show <skill>The evidence for one skill: a daily histogram and its most recent events, each with its log location.
skima statusChecks every agent home's links and settings. Changes nothing.
skima syncFixes the links. Replaces install.sh.

Layout example from the spec. The numbers are made up.

How to read it: sess is the headline, the number of root sessions with a strong load. read and ref sit in their own columns. agents shows letters: C for Claude, X for Codex, P for Pi. The * after 9.1 means the skill changed after its last grade, so the grade may be out of date. skima checks this with git: if any commit touched the skill after the commit that added the grade, the grade is stale.

The footer matters. "Unused since 2026-09-10 on Claude" is a different claim from "never used", and skima always says which one it means.

Finding dead skills

skima unused lists skills with no strong load in the last 60 days. Two rules keep it from giving bad advice.

A skill your used skills depend on is "held"

Some skills are rarely called directly but are cited by others. blast-radius is the clearest case. Seven skills say things like "owned by the blast-radius skill": interrogate, diagnose-bug, break-invariants, review-audit-fixes, validate-resolve-issue, triage-finding and validate-findings-backlog. writing-for-agents is cited by 20 skills.

skima builds this citation map by reading each skill's text and looking for three patterns: the B skill, owned by B, and B/ in a path. It skips the frontmatter description, because descriptions name neighbouring skills to mark boundaries, not to depend on them. Today 16 of the 29 skills are cited by at least one other.

If validate-resolve-issue was used last week, then blast-radius is held. It appears with its holder and is not suggested for retirement, even with zero direct loads.

Skills that only cite each other are a "cluster"

If the whole goal suite is unused, and its skills only cite each other, none of them holds the others up. They are all listed as unused, with a note naming the group, so you can decide on them together.

$ skima unused
window: 60 days · claude since 2026-09-10 · codex since 2026-03-29 · pi since 2026-08-29
goal-plan           unused   cluster: goal-smart, goal-execute
goal-execute        unused   cluster: goal-smart, goal-plan
some-new-skill      new      first commit 2026-10-01
blast-radius        held     by validate-resolve-issue (2d ago), interrogate (5d ago)

Illustrative output, not a measurement of your usage.

Skills younger than the window are marked new, and skills with only reads are flagged weak-only.

Keeping homes in sync

Your skills live in one place, ~/dotfiles/skills/. Each agent home gets a symlink per skill pointing back there. skima never copies files and never rewrites a skill for a particular agent. All three agents read the same SKILL.md.

The homes are listed in one config file, ~/dotfiles/skills/skima.toml. Adding a home there turns on linking, policy checks and usage tracking for it at once. That is what prevents the next ~/.claude-work gap.

[[home]]
name  = "claude-work"
agent = "claude"
path  = "~/.claude-work"

Policy checks

skima also checks the rules install.sh checks today:

  • Each skill's name matches its folder, uses lowercase words joined by hyphens and is at most 64 characters. Its description is non-empty and at most 1024 characters.
  • No skill sets disable-model-invocation.
  • Each skill's agents/openai.yaml sets allow_implicit_invocation: false, so Codex only loads it when asked.
  • Each Claude home's settings.json exists and marks every skill "name-only", so Claude only sees skill names until it asks for one.

skima never edits your settings files. When something is missing it prints the exact line to add.

It also warns when the last scan is close to falling outside Claude's 30-day window: with default settings, any time the last scan is more than 23 days old. Running any usage report scans and clears the warning.

All or nothing

sync works out every change first and only then writes anything. If any home has a conflict, such as a real folder where a link should go, it prints the mv or rm that would fix it and exits without touching any home. It has no --force and never makes backups. Running it a second time prints nothing.

Replacing install.sh

Two tools managing the same links would drift apart, so skima takes over everything install.sh does and the old script is deleted in the same commit. The steps:

  1. Run both tools side by side on throwaway copies of a test home and compare the results file by file. Paste the output into the commit message.
  2. Delete skills/install.sh.
  3. Port its tests to drive skima sync.
  4. Update every reference to it (the skills README, GOAL_SKILLS_USAGE.md, the Pi integration test, the dotfiles README) until a search for install.sh comes back empty.
  5. Add a step to the top-level dotfiles installer that clones skima, installs it with cargo install and runs skima sync.

The cost: a fresh machine now needs a second repo and a Rust toolchain to install skills. The spec accepts that so skima can have its own tests and releases.

How we'll know it works

Each milestone is done when a run passes and its output is pasted into the commit. Reading the code doesn't count.

  • One test per log shape. Every known record shape, both real loads and look-alikes, gets a test built from a real record on this machine with the text scrubbed. For example: a Codex fork pair whose copies must become one event, a /clear that must produce nothing, and a skill name quoted in tool output that must produce nothing.
  • Two independent counters. Two agents each write their own counting script from the spec alone, without seeing skima's code. skima's counts must match both.
  • Precision check. Two reviewers each sample 20 strong events, 20 reads and 20 near misses and judge them against the source line. Strong loads must be at least 95% correct. The read accuracy goes in the README, whatever it turns out to be.
  • Crash and repeat tests. Scan twice and nothing new is added. Delete the bookmarks and nothing new is added. Cut a line in half, scan, finish the line, and exactly one event appears.
  • Live runs. A throwaway probe skill is loaded for real by claude -p, codex exec and Pi, and skima must report exactly those three loads.

skima also warns you when a log file mentions a skill marker but produced no event. That is the alarm for an agent changing its log format.

What the first build measured

  • The first scan of this machine read all 469 Pi sessions, 6,111 Codex sessions and 1,858 Claude sessions in about 18 seconds. A second scan added nothing and took 0.2 seconds.
  • Two independent counting scripts, written from the spec without seeing skima's code, found the same strong loads as skima, ID for ID: 191 slash, 137 tool and 644 typed.
  • Two reviewers checked 80 sampled events against their source lines. All 40 strong loads and all 40 reads were correct, and 40 sampled near misses hid no real load.
  • All 18 tests of the old install.sh pass against skima sync. On this machine skima status reports one error: claude-work: missing break-invariants.

Build order

The ledger ships first. Until the first real scan, Claude keeps deleting its oldest logs one day at a time, although old typed /name commands can still be recovered from history.jsonl.

M02 to 3 days. The log readers, the ledger and scan, then the first real scan of this machine.
M12 days. usage, unused, show, grades and the citation map. The precision check and live runs pass.
M21 day. status, read-only. It must report only the missing break-invariants.
M32 days. sync, the side-by-side check against install.sh, then deleting install.sh.
M4Only when needed: retire (moves a skill to .archive/ and refuses if it is held or recently used), runs for the retro skill, a report on skills the model loads without being asked, and support for other agents.

Two questions are left open, and both will be settled by a run. Does current Codex still find skills in ~/.codex/skills, or only in ~/.agents/skills? The live codex exec test answers it. And does the work profile need its own CLAUDE.md for your AGENTS.md rule to apply? That one is outside skima.

What it won't do

  • No teams, accounts, cloud sync or web dashboard. Syncing across machines is git's job.
  • No judging skill quality. A load is not the same as a skill being followed well; grade and retro cover that.
  • No storing prompts, command arguments or skill text.
  • No editing harness settings files.
  • No project-level skills inside individual repos.
  • No support for agents that aren't installed here (Cursor, Windsurf, Amp, Kiro, Gemini CLI) until there are real logs to test against.
Known limits. Claude sessions deleted before the first scan are gone, except typed /name commands recovered from history.jsonl. Reads with unusual commands, such as awk or python -c, are missed, but skima counts and shows the commands it couldn't parse. The agents' log formats are undocumented (Pi's is the exception), so every event records the agent version.
