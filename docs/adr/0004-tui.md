# 0004. Terminal UI

Status: Accepted (2026-11-26)

## Context

The TUI of bare `mazo`, the `mazo add` picker and the shared palette carried their design decisions as code comments. The comment ban (ADR 0001) removes those comments. This record keeps the decisions that the code alone does not explain: why each action takes the path it does, how a job and its questions resolve, which ratatui behaviours are worked around, and why the tests are built as they are.

## Decisions

### App and run loop (`tui::App`, `tui::run`)

- The TUI renders from the typed report model. A card is the text `report::card_text` prints for `show`. Every action (`retire`, `sync`, `add`, `update`, `audit`) asks first and runs its CLI command's own code path. Add, update and audit run on a background thread, at most one at a time, and report in the job pane.
- `Data` owns everything an `Input` borrows, so an action can reload it and a job can take a clone to its thread.
- `App::reload` runs after every action and every finished job, so the views show the new state: a new audit on the card, a newly added skill in the usage table. A card whose skill is gone, such as a retired one, closes back to its list.
- `App::refresh` clamps the selection only when the current list is the usage view. Changing the agent filter on a card opened from the unused list therefore leaves the unused selection where it was.
- `App::clear` makes the run loop clear the whole terminal before the next draw. An action or a scan may have written progress output under the screen.
- `run` enables bracketed paste, so a paste arrives as one event and a newline in it cannot submit a dialog. `App::paste` inserts into the add source dialog only and does nothing anywhere else.
- `run` wraps the panic hook that `ratatui::init` installs and calls it only for panics on the UI thread, after turning bracketed paste off. A job's panic is caught in the job (`caught`) and shown in its pane, and the screen stays up.
- While a job runs, the run loop polls input with a 100 ms timeout, so the job's lines and spinner redraw as they arrive and navigation keeps working.

### Actions and dialogs (`tui::dialog`)

- An `Act` applies at once on `y` through the same function as its CLI command (`lifecycle::retire`, `links::apply`), and `App::act` reloads the data afterwards. Any key then closes the result dialog.
- The TUI never passes `force`. `App::act` calls `lifecycle::retire` with force off. `App::update` runs `store::update` without force, so a judge's security finding still refuses an update. `App::add` runs `store::precheck` up front to show `add`'s early refusal, then calls `store::add` with `force`, `trust` and `yes` all false. The TUI has no `--force` path.
- `Act::Sync` carries the exact `Plan` the dialog displayed, so `y` applies what the user saw. `synced` takes the data lock, re-reads the inventory and re-plans with `links::checked`. It applies the confirmed plan only when the fresh plan's actions are identical, and refuses otherwise.
- `App::retire` and the `s` key refuse with the one-job dialog while a job runs, because their plans read an inventory the job may change. `App::one_job` refuses a second job for the same reason.
- `Ask::Answer` replies with the default on Enter and with true or false on `y` or `n`. Esc answers No. A Ctrl or Alt chord, and any other key, leaves the question open. `q` asks to quit, which drops the reply sender, and the job reads the unanswered question as No.
- `App::quit` exits at once when no job runs. Otherwise it opens an `Ask::Quit` dialog that holds the dialog it interrupted. `y` stops the job and quits. Any other key restores the interrupted dialog, still unanswered, so a pending add question can still end on its No.
- `draw_dialog` wraps a line wider than the screen at spaces instead of truncating it, and bolds a question's first line as its headline.
- `typed_line` keeps the last columns of the typed source and marks the cut with `…`, so the cursor stays visible.

### Background jobs (`tui::job`)

- A `Question` whose dialog closes without a reply resolves as No, or as nothing picked. `Dialogs::yes_no` and `Dialogs::pick` read a dropped reply channel as false or empty.
- `Dialogs::confirms_calls` returns true because the TUI picker can select several skills without `--all`, so judge calls are confirmed for any untrusted add.
- `App::stop` sets the job's cancel flag, which kills the judge call in flight, then waits at most `STOP_WAIT` for the thread. `STOP_WAIT` is twice `KILL_GRACE`, the time a judge gets to exit on SIGTERM before it is killed, so quitting outlasts the judge. While waiting, `App::stop` drains pending questions and drops their reply senders, so the job reads each one as No and does not block.
- `caught` wraps the job in `catch_unwind` and turns a panic into a failed result that names its message, so the job pane shows it and the TUI stays up.

### Keys (`tui::keys`)

- Enter on an unused store skill opens the retire dialog instead of its card, because such a skill is already past its install-date window.
- An open dialog takes keys before any screen binding, so `H` is a literal `H` while the add source or the filter is being typed.
- `H` opens the help on any screen. `help::lines` puts the current list's columns first, then the marks and the FAQ answers.
- A page move on a card moves by the card's visible height (the value `draw_card` returns), not the list's.

### Tables and top bar (`tui::draw`)

- `fit` applies the `NARROWING` steps in order, each only while the table still overflows. A column not listed never narrows, and a `Narrow::Cut` column is never dropped. The order drops the usage columns one at a time, folds `slash` and `tool` into `via`, and cuts the unused list's notes before skill names, so skill, sess, 30d, trend, last, grade and audit stay down to 60 columns.
- `fit` gives the spare width to the first and last columns. On a wide terminal the skill and audit columns share it, the count columns keep their width, and the selected row's highlight runs edge to edge.
- `table` never styles the first (skill) column, so a skill name that matches a status token never takes a status colour.
- `App::tabs` computes the tab width as each title plus a space either side, plus a one-column divider between tabs, to match ratatui's `Tabs` layout.
- From `WIDE` (140) columns the usage view gives 40% of the width, at least 50 columns, to the selected skill's card behind a rule. Narrower terminals show no side card, and Enter still opens the card.
- `App::top` ends the top bar with each agent's tokens in context. An agent at 80% of its listing-budget share of the context window (1% for Claude, 2% for Codex, `Tokens::agents`) shows in the warning colour. When the chips crowd the tokens, the label shortens and every agent's value and colour stay in view. The missing-bundled-skills notice takes a second row when it does not fit beside them, and the row goes once those skills are installed.
- The footer (`keys`) lists only the `KEYS` that work on the current screen. An empty list says why instead of showing an empty table.

### Card and chart (`tui::card`)

- `draw_card` renders the whole card into an off-screen `Buffer` and copies only the visible rows, so the activity chart scrolls together with the card lines.
- `draw_activity` blanks ratatui's bar value with `text_value("")` and writes each count itself. ratatui hides a value as wide as a short bar and any value on an empty bar. Bars widen to the widest label or count, so every bar shows its count. A chart cut to the newest buckets says so in a note after the heading.
- The chart counts strong sessions per bucket of the card's window, as `report::buckets_of` buckets it. `w` cycles the window, which re-buckets the chart in days, ISO weeks or months. Today's partial bucket is muted.
- `sgr` interprets only the SGR codes `crate::render` emits (1 for a table header, 31 red, 33 yellow, 0 reset) and ignores any other code.

### Logo (`tui::logo`, `tui::logo_art`)

- `Logo` is baked into half-block cells: the cards keep the image's fixed colours and the wordmark uses the terminal foreground (`Color::Reset`), so it reads on dark and light themes.
- `Logo::render` uses `INK` only as a foreground colour. `Color::Reset` as a background would be the terminal background, not its text colour.
- `logo_art.rs` is generated from `docs/assets/logo-dark.png` by `docs/assets/bake-logo.py`. Regenerate it instead of editing it by hand. `LOGO` holds one pixel row per array row, two rows per terminal cell, each pixel 0 for none, `INK`, or `0xRRGGBB`.

### Picker (`pick`)

- `Step::Done` carries the selected paths in list order, and an empty list on cancel. Cancelling and picking nothing are the same reply.
- `pick` restores the terminal on every return, and on a panic through the hook `ratatui::try_init` installs.

### Theme (`theme`)

- `theme` uses named ANSI colours so the terminal's own theme picks the shades. Only the selection background (`selected`) is a fixed grey.

### Tests (`tests/tui.rs`)

- The TUI tests render views into ratatui's `TestBackend` from the golden fixture, drive actions by key events against a temp config and a stub judge, and run the binary on a pseudo-terminal.
- `app` builds the test app over the golden fixture with a nonexistent data directory, because its views read none.
- `stub` and `Actions::vetter` write command judges that append their pid to `<root>/pids`. While `<root>/hang` exists they become a `sleep` that ignores the hangup of a closing terminal, so only mazo's kill ends them and the tests can check that it happened.
- `Actions::hosted_repo` serves a temp repo under `https://git.example.org/acme/` through a process-wide git `insteadOf` rewrite set once. This gives a source with a host to trust, so the tests can show that an untrusted skill is re-vetted on update while a trusted-host skill needs no judge.
- SAFETY of `hosted_repo`'s `set_var`: all environment access in the test binary goes through std, which serialises it under its lock (a spawn's PATH lookup too), and no test does network or DNS lookups. `GIT_CONFIG_COUNT` is set last, so a git spawned meanwhile sees the whole rewrite or none.
- `on_a_pty` runs bare `mazo` under `script` on an 80x24 pseudo-terminal. It writes each step's keys only after the `\x1b[?1049h` sequence appears, because the TUI enters the alternate screen after raw mode and only bytes written after that are read as keys.
- The judge-refusal test joins wrapped dialog lines before matching, because a long origin path, such as macOS temp directories give, pushes the refusal onto two lines.
