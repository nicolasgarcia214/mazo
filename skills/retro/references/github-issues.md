# GitHub Issue Filing Mechanics

Detailed mechanics for Phase 4 of the retro skill: label definitions, recommendation-parsing field definitions, command templates, the issue-body template, and report-update mechanics. The behavioral rules (skip diagnostics, the mandatory user gate, failure isolation) live in SKILL.md Phase 4.

## Labels

Create (or update) these labels with `gh label create --force -R {repo} "{name}" --color {color} --description "{description}"`:

| Label | Color | Description |
|-------|-------|-------------|
| `retro` | `1d76db` | Generated by skill retrospective |
| `retro:immediate` | `d93f0b` | Fix before next run |
| `retro:structural` | `fbca04` | Skill design change |
| `retro:process` | `0e8a16` | Workflow improvement |

If any label creation fails, log the warning but continue — issue creation can proceed without the tier label.

## Recommendation Parsing — Field Definitions

From the Phase 3 report (already in memory), extract for each recommendation bullet:

1. **Tier**: from the subsection header (Immediate / Structural / Process).
2. **Title**: the bold text between `**...**`.
3. **Prescription**: the text after the bold title.
4. **Failure summary**: identify the most relevant entry from `## What Went Wrong` and capture the core problem plus its impact in 1-2 sentences.
5. **Supporting evidence**: pull 2-4 concrete facts from the report sections most related to this recommendation. Prefer, in order:
   - the matching `## What Went Wrong` item
   - relevant `D3`, `D5`, or `D6` analysis
   - `Failed Command Analysis`, token metrics, or gate/phase notes
   - the executive summary if it contains the clearest context
6. **Likely touchpoints**: collect any explicit file names, scripts, tools, phases, or workflow components that appear relevant in the recommendation or supporting evidence.
7. **Acceptance criteria**: derive 2-4 concrete, observable checks that would let a developer verify the fix is complete.
8. **Category label** via keyword matching on the full recommendation text:
   - Contains "fix", "bug", "broken", "error", "failure" → `bug`
   - Contains "token", "budget", "polling", "waste", "efficiency" → `performance`
   - Default → `enhancement`

Each issue gets three labels: `retro` + tier label (`retro:immediate` / `retro:structural` / `retro:process`) + category label.

## Issue Creation Command

```
gh issue create -R {repo} \
  --title "[retro] {title}" \
  --body "{body}" \
  --label "retro" --label "{tier-label}" --label "{category-label}"
```

## Issue Body Requirements

- The issue must be self-contained and understandable without opening the retro report.
- Include enough detail for a developer to understand the current problem, why it matters, where to start, and what "done" looks like.
- Prefer concrete facts over generic prose. Reuse report evidence, commands, phases, file names, and metrics whenever available.
- If the issue is about efficiency or process, include the wasted time/token/tooling impact so the tradeoff is explicit.
- Omit empty sections, but do not collapse the issue into a one-paragraph summary.

## Issue Body Format

```markdown
## Summary
[2-4 sentence developer-facing summary of the problem, desired change, and expected outcome.]

## Retro Context
- Skill: `{skill-name}`
- Date: `{date}`
- Verdict: `{VERDICT}` ({score}/5)
- Tier: `{Immediate|Structural|Process}` — {tier description}
- Category: `{bug|performance|enhancement}`

## Problem
{failure summary}

## Evidence
- [Specific report fact, file, command, phase, or metric]
- [Specific report fact, file, command, phase, or metric]
- [Specific report fact, file, command, phase, or metric]

## Recommended Change
{prescription expanded into implementation-oriented guidance}

## Likely Touchpoints
- `[file, script, tool, phase, or workflow component]`

## Acceptance Criteria
- [Observable outcome]
- [Observable outcome]
- [Validation step or regression guard]

## References
- Retro report: `{retro-report-filename}`
- Related sections: `{section names used for evidence}`

---
_Auto-generated by the retro skill._
```

Capture the returned issue URL and number for each created issue. If an individual issue creation fails, log the error and continue with the remaining issues.

## Report Update Mechanics

Update the retro report written in Phase 3 step 9 (prefer `Edit` for targeted changes over rewriting the whole file):

1. **Inline annotation**: Append `[TRACKED](issue-url)` to each recommendation bullet that was filed:
   ```
   - **Fix report rendering**: Investigate why... [TRACKED](https://github.com/owner/repo/issues/42)
   ```
2. **Summary table**: Insert a `## Filed Issues` section after `## Recommendations`:
   ```
   | # | Recommendation | Issue | Labels |
   |---|----------------|-------|--------|
   | 1 | Fix report rendering | [#42](url) | retro, retro:immediate, bug |
   ```
3. **Frontmatter**: Add `github_issues` (list of issue numbers) and `github_repo` fields to the YAML frontmatter.

If the report file cannot be found, log a warning and skip the report update — the created issues still stand.
